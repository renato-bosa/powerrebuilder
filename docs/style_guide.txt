Project Style & Formatting Guide

A consistent snake_case naming scheme with verb_noun for actions, noun_verb for data, and controlled exceptions.

⸻

1. General
	•	All identifiers (scripts, modules, functions, variables, constants, props) use snake_case.
	•	Word-count:
	•	Two words (one_word_two): preferred for clarity.
	•	One word (clear): allowed if immediately unambiguous.
	•	Exception: nested substructures may use three words (base_qualifier_subqualifier) to indicate an extra layer.

⸻

2. Python Scripts & Functions
	•	Script filenames (in pbtool/):
	•	Prefer verb_noun.py (e.g. extract_pbl.py).
	•	One-word allowed if universally understood (e.g. serve.py, login.py).
	•	Function / method names:

def extract_pbl(...):          # preferred two words
    ...
def parse(...):                # single-word OK if clear
    ...
def test_user_creation_flow(): # three-word for tests
    ...


	•	Tests must start with test_ and may use three words:

def test_parse_window_nested_if():
    ...



⸻

3. Variables, Constants & Properties
	•	Variables & properties (noun_verb preferred):

user_count      # preferred two words
count           # single-word OK if clear
file_path       # two words
path            # single-word OK if clear


	•	Constants (same rules, optionally UPPER_SNAKE_CASE):

max_retries
TIMEOUT         # clear single-word constant



⸻

4. Subclass & Substructure Naming
	1.	Default (two-word)—suffix style:

control_button
control_checkbox


	2.	One-word for base classes or very generic types if clear:

control   # base class itself
button    # when context implies control_button


	3.	Three-word exception—nested under a two-word name:

control_button_primary    # primary variant of control_button
control_button_secondary



⸻

5. Frontend Components & Props (TypeScript/Astro)
	•	Component filenames: snake_case; verb_noun preferred, but one-word allowed:

window_page.astro
login.astro                # clear single-word


	•	Event-handler props always use noun_verb with on_ prefix:

interface ButtonProps {
  on_click: () => void
  on_focus: (e: FocusEvent) => void
}



⸻

6. Formatting & Layout
	•	Indentation:
	•	Python: 4 spaces
	•	TypeScript/JS: 2 spaces
	•	Line length:
	•	Python: ≤ 88 characters
	•	TypeScript/JS: ≤ 100 characters
	•	Blank lines:
	•	2 between top-level definitions (modules, classes, functions)
	•	1 between methods or logical blocks
	•	Imports (Python): grouped in order:
	1.	Standard library
	2.	Third-party libraries
	3.	Local project modules
	•	Docstrings (Python): triple-quote, one-line summary + optional details.
	•	Comments:
	•	Inline: # explain why (not what)
	•	Block:

"""
Longer explanation or example
"""



⸻

7. Summary of Word-Count Rules

Context	Pattern	Word-count	Example
Scripts & Functions	verb_noun (one-word allowed)	1 or 2	serve, extract_pbl
Variables & Constants	noun_verb (one-word allowed)	1 or 2	count, user_count
Tests	test_unit_scenario	3	test_parse_window_nested_if
Subclasses	base_qualifier	2	control_button
Nested Substructures	base_qualifier_subqualifier	3	control_button_primary


⸻

Stick to this guide so all code—Python and Astro—remains consistent, readable, and predictable.
